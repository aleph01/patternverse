A walking group wants new members to feel welcome. Its organizers quickly suggest friendly messages, name badges, and a better website. Then someone asks a different question: “If we wanted a newcomer to feel that this group was not for them, what would we arrange?”

The answers arrive quickly: assume everyone knows the meeting point, use unexplained shorthand, leave at an uncertain time, and keep conversations inside existing friendships. Several of those conditions already exist.

Inversion examines the unwanted result and the conditions that could produce it. The change in direction can reveal requirements and failure paths that remain invisible while you concentrate only on the desired outcome. It is a broad reasoning move with a long mathematical and practical history, not a framework that needs a single modern inventor.

## Define a specific unwanted outcome

“Fail” is too vague. For the walking group, the unwanted result might be “a first-time participant cannot find the start or leaves feeling unable to join the conversation.” This makes the exercise concrete and keeps it connected to a real experience.

Ask how you could reliably produce that result. Imagine arrangements, information gaps, incentives, and timing. Avoid making the list a set of insults about people. “Have inconsiderate organizers” is less useful than “publish a meeting location that only regular members recognize.”

You are constructing possible mechanisms, not predicting that every listed problem will occur. Mark which are already observed, which are plausible, and which are remote possibilities. The exercise should improve attention, not turn every imagined failure into an urgent threat.

## Turn causes of failure into design requirements

The group can translate “use an ambiguous location” into “provide an address, a recognizable landmark, and a contact route.” “Keep every conversation among regulars” could lead to a host greeting newcomers and helping them join a small conversation.

Check that the translated requirement actually interrupts the mechanism. Adding a contact number helps only if somebody can answer it at the relevant time. A host role helps only if a person accepts it and the arrangement does not make newcomers feel singled out.

The opposite of a bad condition is not always a sufficient solution. “Never leave anyone uncertain” is impossible. A useful requirement might instead be “explain the route and the options for leaving early before the walk starts.” It addresses a concrete uncertainty within the organizers’ control.

## A second example: keeping a small archive usable

Suppose you want a family archive to remain understandable years from now. Invert the aim: how could you make the files practically unusable? You could give everything generic names, keep the only copy on one device, omit context, choose formats no one can open, and let different relatives maintain conflicting versions without explanation.

Those mechanisms suggest distinct safeguards: meaningful descriptions, an appropriate backup arrangement, provenance notes, usable formats, and a clear convention for changes. They also expose trade-offs. Recording every possible detail may make the project so laborious that nobody begins.

Choose safeguards proportionate to the archive’s value and the available effort. A modest consistent description can be more useful than an elaborate catalog that remains empty. Inversion should help prioritize protection, not create an unfinishable demand for perfection.

## Separate inversion from a premortem

[[run-a-premortem|Run a Premortem]] imagines that a particular plan has already failed and asks what caused it. Inversion can begin before a plan exists. You can design a bad system deliberately, identify what makes it bad, and derive requirements for a better one.

The distinction matters. If the walking group has not chosen an onboarding plan, asking why “the plan failed” may keep attention on an arbitrary imagined solution. Starting from the unwanted newcomer experience opens the search more broadly.

[[second-order-thinking|Second-order Thinking]] follows consequences beyond an immediate effect. It complements inversion when a safeguard might create another problem: a rigid check-in process could make a friendly walk feel bureaucratic, for example.

## Inspect the assumptions in the negative story

A vivid account can feel convincing without being likely. Ask what evidence supports each failure mechanism and under which conditions it would not operate. In a familiar group, some shorthand may be harmless if clear explanations are also available. A backup system can reduce one risk while introducing a maintenance responsibility.

Do not equate avoiding the worst outcome with achieving the desired one. A newcomer who finds the start and completes the walk may still not feel welcome. Negative requirements establish part of the design; positive experiences still need attention.

Use inversion when you are stuck repeating obvious improvements, when failures would be costly, or when minimum conditions need clarification. Avoid using it as a ritual for dismissing every new idea. The point is to improve a possibility, not to prove that action is dangerous.

## End with a useful intervention

Choose a small set of important mechanisms. For each, identify a prevention, an early signal, or a recovery action. Some causes are best removed; others can only be detected and managed. Assign responsibility where the plan requires it, and check that the responsibility has actually been accepted.

Keep a final check against the positive goal. For the walking group: would the proposed changes help a real newcomer participate with confidence and dignity? If the safeguards protect the organizers while making participation harder, the inverted exercise has served the wrong objective.

## Discover what to stop doing

Some inverted exercises produce a new list of safeguards while leaving counterproductive routines intact. A different application asks which harmful arrangements already resemble current behavior. If the walking group wants to welcome newcomers, does it still announce the meeting point in shorthand only regulars understand? Does a host introduce themselves and then immediately return to a familiar conversation? Recognizing an existing pattern changes the task from inventing more improvements to making room by stopping something.

The Liberating Structure **Creative Destruction**, also called **TRIZ**, was developed by Henri Lipmanowicz and Keith McCandless. Participants imagine ways to guarantee a bad result, recognize similarities to current practice, and identify what to stop with first steps. This is a particular facilitated application of inverted thinking. The name should not be read as a claim that the worksheet implements the broader engineering TRIZ system.

For the walking group, stopping unexplained location shorthand might mean replacing it with a description a first-time visitor can use. Stopping a long opening speech could create space for a short welcome in pairs. These changes are not simply the grammatical opposites of bad practices. They are arrangements intended to interrupt an observed mechanism while serving the positive aim.

The reckoning needs evidence. A participant may recognize a resemblance without knowing how often it occurs or what explains it. Label that as something to check. An imagined worst case is not proof that colleagues are producing it deliberately. Keep the exercise focused on behaviors, incentives, information, and arrangements rather than constructing a comic villain who resembles somebody in the room.

## Stop within actual authority

A routine may protect a function its critic does not see. Before stopping an announcement, check whether it contains information newcomers need. Before dropping a review, check who relies on it. A stopping proposal should identify affected people, obligations, and the agreement needed to change the arrangement. Making space for innovation does not justify silently removing another person's boundary.

The same inquiry can help with a personal commitment. Someone trying to read regularly may notice that they always begin by comparing new reading apps. Stopping that search during the planned reading period creates room for the intended activity. It is an observed pattern they can change, rather than a new claim that preparation is always avoidance. A later review can ask whether reading actually increased.

[[discover-what-to-stop-doing]] is a separate participant-led practice for this application. The existing Design the Failure, Then Remove Its Causes practice below remains available for deriving positive safeguards and recovery actions. Choose the stop-doing variant when current habits or arrangements deserve scrutiny, and the broader practice when the main task is designing against possible failure. Both should return to the useful experience the person is trying to create.

## Practice — Design the Failure, Then Remove Its Causes

**Purpose:** Investigate how an unwanted result could be produced, then translate that knowledge into useful constraints.

**Time:** About 15 minutes. The practice produces a reflection or plan; it does not execute actions for you.

```patternverse-language
:language 1
:title "Design the Failure, Then Remove Its Causes"
:output result

!show {
About 15 minutes. Work with one manageable situation. This participant-led practice needs no AI. Review each group before Continue. The result is a reflection or plan; actions are not carried out or scheduled for you.
}
context = !form {
:title "Define success and its opposite"
desired = !ask {
What concrete outcome do you want?
}
unwanted = !ask {
What specific unwanted outcome will you invert toward?
}
boundary = !ask {
What people, resources, or obligations must remain protected?
}
}
mechanisms = !collect {
:min 1
:max 6
entry = !form {
:title "Add an entry"
failure = !ask {
What arrangement or action could reliably contribute to the unwanted result?
}
how = !ask {
How would it produce that result?
}
status = !choose {
What evidence supports this mechanism?
- observed: "Direct observations"
- indirect: "Indirect support"
- hypothesis: "A hypothesis to check"
}
countermeasure = !ask {
What prevention, early signal, or recovery action could interrupt it?
}
}
-> yield entry
}
!show {{mechanisms}} {

}
review = !form {
:title "Build a positive design"
priority = !ask {
Which mechanisms matter most, given likelihood, consequences, and evidence?
}
proposal = !ask {
What proportionate safeguards will you incorporate?
}
positive = !ask {
How will the design also produce the desired experience, beyond avoiding failure?
}
next = !ask {
What check or action comes next, and who needs to agree?
}
}
result = {aim: context, failure_mechanisms: mechanisms, design: review}
!show {
Your proposed safeguards: {{review.proposal}}
Check the positive experience: {{review.positive}}
Next action or agreement: {{review.next}}
}
-> end
```
