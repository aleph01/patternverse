      Execution rules and limits
      

        The scripted model requests reserve_inventory with exactly item="tripod" and an integer
        quantity from 1 to 10. The host validates that contract, requires the clerk role and
        confirmation, and attaches the key demo-17 to the checked request. The role and confirmation
        selectors simulate policy; they are not authentication or real consent for a real booking.
      

      

        One read-only lookup always runs first and counts as one tool attempt. Rejected host
        proposals cause no write attempts. The service rejects quantities above current stock. A
        successful write atomically reduces stock and stores its result under the request key. A
        retry with the same key and identical item/quantity returns the stored reservation; changed
        parameters under that key are rejected. State is in-memory and sequential, not durable or
        concurrent.
      

      

        The loss setting drops only the first successful write response, after commit. Error
        responses are delivered. One or two write attempts are allowed; a second attempt occurs only
        after that simulated loss. UNKNOWN means the client lacks a receipt. The simulator exposes
        the committed reservation separately; the client does not infer it. No general retry
        scheduler, backoff, reconciliation API, rollback, prompt-injection defense, real identity
        service, network, model selection, or generated reply is simulated.
      

      

        The same key applies only to this one logical request and its retry. Every changed input
        starts an independent fixture with an empty ledger; reusing demo-17 across different real
        operations would be incorrect. The two write attempts use exactly the same immutable
        envelope. Stop after a terminal receipt, a policy gate, or the attempt budget. Total tool
        attempts = one lookup + executed write attempts.
